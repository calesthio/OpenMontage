## 0. ВОЗОБНОВЛЯЕМОСТЬ (новое в V7 — критично для многочасовой работы без присмотра)

Паттерн "state machine, не транзакция": каждый шаг ниже должен быть
БЕЗОПАСНО ПОВТОРИМ — если сессия Codespaces оборвётся и запустится
заново, повторный проход по уже сделанному шагу не должен его
сломать или задублировать.

Перед началом ЛЮБОГО этапа:
1. Прочитай docs/BUILD_LOG_V7.md (создай, если нет) — если там уже
   есть запись о завершении этого этапа — пропусти его, иди дальше.
2. Каждый значимый шаг — отдельный коммит СРАЗУ по завершении (не
   накапливай несколько шагов в один коммит) — коммит и есть точка
   восстановления.
3. Любая операция, создающая файл — проверяй, существует ли он уже
   с ожидаемым содержимым, прежде чем создавать заново (idempotent
   write: если файл есть и валиден — пропусти генерацию).
4. В начале КАЖДОЙ новой рабочей сессии (в том числе после обрыва) —
   первым делом прогони `git log --oneline -20` и прочитай последние
   записи BUILD_LOG_V7.md, чтобы понять, где находишься, прежде чем
   действовать.

истории.

## 3. АРХИТЕКТУРА ФАБРИКИ — пять именованных слоёв

Формализуем пайплайн как пять явных слоёв (так проще диагностировать,
где проблема, и так это принято называть в индустрии автоматизации
видео — Research → Voice → Visuals → Assembly → Publish-prep):

```
СЛОЙ 1 — RESEARCH/SCRIPT
  lib/script_engine.py — сценарий, структура hook-delivery cycle
  (см. раздел 4.2), проверка факт-чекинга по научным источникам
  (NASA/научные публикации > блоги > форумы — см. матрицу раздела 2)

СЛОЙ 2 — VOICE
  lib/tts_engine.py — Kokoro (основной) + Piper (CPU-фоллбэк)
  lib/audio_mixer.py — громкость (-16 LUFS цель), true peak,
  музыка/SFX, fade

СЛОЙ 3 — VISUALS
  lib/footage_sourcing.py — архив (NASA/Archive.org/Wikimedia) с
  манифестом лицензий
  lib/image_generation.py — Nano Banana 2.1, фотореалистичный
  system-промпт, retry-логика, учёт квоты (budget_guard.py)
  lib/color_match.py — согласование archival+AI по сцене
  lib/scene_router.py — archival vs ai_generated по сцене

СЛОЙ 4 — ASSEMBLY
  lib/motion_director.py — camera pan/zoom/reveal; ОБЯЗАТЕЛЬНАЯ
  проверка: ни один статичный план не длиннее 15 сек без визуального
  изменения (см. раздел 4.1 — численный критерий)
  lib/qc.py / illustration_qc.py — техническая QC + slideshow risk
  score + retention_pacing_score (новое, раздел 4.1) + pre-compose gate

СЛОЙ 5 — PUBLISH-PREP
  scripts/release_checklist.py — полный QC + сборка publish-ready
  package одной командой
  publish_package/ — файл, описание, теги, превью-кандидаты, главы

budget_guard.py — ЕДИНАЯ точка проверки бюджета перед любой тратящей
операцией, используется всеми слоями

docs/
  PIPELINE_REUSE_GUIDE.md
  QUALITY_RESEARCH_LOG.md
  BUILD_LOG_V7.md
  PROPOSALS_FOR_OWNER.md
```

Каждая функция в lib/ должна возвращать явный статус
(success/fallback_used/failed) — не падать молча. Это контракт для
всех модулей: любой слой, встретив ошибку, обязан либо сам
восстановиться (fallback), либо чётко сообщить о сбое в лог, но
никогда не останавливать всю фабрику целиком из-за сбоя в одном
модуле — переходи к следующей задаче, возвращайся к сбойной позже.

## 4. ЦИКЛ КАЧЕСТВА — теперь с измеримыми критериями, не "на глаз"

### 4.1. Темп и движение (retention_pacing_score)
Правило, подтверждённое исследованиями удержания аудитории YouTube:
визуальное изменение (смена кадра, значимое движение камеры, появление
нового элемента) должно происходить **не реже чем раз в 8-15 секунд**.
Дольше — статика считывается как застой и роняет удержание.

Реализация: пройди весь final.mp4, посчитай для каждого
непрерывного визуального сегмента его длительность без значимого
изменения. Если сегмент >15 сек статичен — это кандидат на
доработку motion_director (pan/zoom/reveal). Запиши метрику
`max_static_segment_sec` и `avg_visual_change_interval_sec` в QC.
Целевой порог: `max_static_segment_sec <= 15`.

### 4.2. Структура повествования (hook-delivery cycle)
Проверь сценарий по схеме: Хук (вопрос/интрига) → Обещание (что
узнает зритель) → Раскрытие части 1 → мини-хук → Раскрытие части 2 →
... → Финальный вывод. Если в структуре есть провисание (долгий
кусок без новой интриги/вопроса) — это кандидат на сокращение или
добавление промежуточного "mini-hook".

КРИТИЧНО: хук не должен ничего обещать, чего нет в видео. Избыточное
обещание в первые 15 сек бьёт по удержанию в середине видео сильнее,
чем честное, чуть менее эффектное начало — исследования показывают,
что ложные ожидания роняют досмотр, когда обещание не подтверждается.
Сверь текст хука с реальным содержанием видео буквально, предложение
за предложением.

### 4.3. Размещение AI-плашки
Плашка "AI-generated visualization" должна появляться ПОСЛЕ того, как
хук уже захватил внимание (после первых ~2-3 сек, не в самом первом
кадре) — открывать видео логотипом/дисклеймером вместо контента —
известная ошибка, роняющая досмотр с первых секунд. Проверь текущее
размещение, перенеси если плашка идёт раньше хука.

### 4.4. Остальные пункты из V6 (темп нарезки общий, музыкальная
динамика, тайминг субтитров) — выполняй как раньше, но теперь привязывай
каждое решение к измеримой метрике, а не только к сравнению "на глаз"
с референсами.

### 4.5. Ведение исследований
docs/QUALITY_RESEARCH_LOG.md: тема → источник/данные, на которые
опираешься → что протестировал → метрика до/после → решение.

B1. Если `max_static_segment_sec > 15` где-либо — доработай через

предыдущих версий до сравнения метрик).

B4. Сравни qc/baseline_v7.json с метриками новой версии — должно быть
строго не хуже по каждой числовой метрике. Если хуже — не принимай

### Этап C — переиспользуемая архитектура (как в V6, раздел 3 обновлён)

### Этап D — второй эпизод (сценарий + разведка, без генерации активов)

### Этап E — публикационный пакет
Финальный файл (лучшая версия по метрикам), варианты описания, теги,

### Этап F — если осталось время
Возвращайся к разделу 4, ищи дальше. Каждая итерация — коммит,
сравнение с текущим baseline, принимай только если не хуже по
метрикам.
