# OpenMontage YouTube Factory — мастер-план v3: аудит, Kilo, агенты и конвейер

**Версия документа:** v3, 15 октября 2026. Техническая база включает аудит, зафиксированный в предыдущей версии 14 октября 2026; динамические детали следует перепроверять в текущей рабочей копии. Это прицельная проверка ключевых репозиториев, текущих тестов/issue OpenMontage и официальных условий провайдеров. Буквально проверить весь GitHub невозможно; этот документ нужно сверить с результатом read-only аудита Kilo и реальной рабочей копией.

## Короткий вывод

Оставить `calesthio/OpenMontage` основой поиска и монтажа реальных футажей. Не переписывать систему и не добавлять тяжёлые модели до проверки текущих этапов и ресурсов. Построить поверх неё проверенный documentary pipeline: доказательства → сценарий → визуально подходящие футажи → локальная озвучка → монтаж → технический/редакционный QA → ручная публикация.

**Самые важные исправления к прежнему плану:** (1) нельзя без проверки условий строить постоянный большой CLIP-индекс из Pexels; (2) HTTP 200 не доказывает достоверность факта; (3) пороги CLIP и самооценка уверенности VLM не являются доказательством; (4) issue OpenMontage #511 всё ещё открыт; (5) три успешных ролика — лишь smoke/release gate, не доказательство долговременной надёжности.

## 0. Исполнительная версия мастер-плана v3 — шесть рабочих сессий

**Задача:** сначала получить одно качественное английское бизнес-документальное видео, затем — превратить доказанный сценарий производства в воспроизводимый конвейер. Шесть частей — это шесть управляемых рабочих сессий, а не обещание уложиться в шесть календарных дней: длительность зависит от фактического состояния репозитория, оборудования, доступности легальных кадров и выбранной локальной модели озвучки.

**Ключевой порядок:** безопасность и управление Kilo Code → агенты/skills/MCP → проверенные данные и права на активы → короткий вертикальный срез → полный пилот и QA → воспроизводимый конвейер. Не начинай с установки множества моделей и плагинов, перестройки архитектуры или массового скачивания медиа.

### Сессия 1/6 — аудит и стабилизация рабочего места

**Цель:** понять, что реально реализовано, не потерять существующие изменения и обеспечить восстановление после перезапуска.

1. Открыть актуальный репозиторий OpenMontage в рабочем окружении и прочитать `AGENTS.md`, `PROJECT_CONTEXT.md` (если существует), локальные инструкции Kilo, текущий мастер-план и инструкции конкретного pipeline. Не считать файлы из старых отчётов подтверждением нынешнего состояния.
2. Только read-only: записать `pwd`, `git status --short --branch`, `git log -1 --oneline`, активную ветку/HEAD, diff, изменённые и неотслеживаемые файлы. Проверить запущенные процессы, lock-файлы и checkpoints — только смотреть, не завершать и не удалять.
3. Составить карту фактически реализованных стадий, доступных команд и тестов; проверить `pipeline_defs/documentary-montage.yaml`, routing провайдеров, бюджетный guard, source adapters, контракты manifests и рендер/QC. Отделить реализованное от TODO/исторических упоминаний.
4. Сверить статус issue #511 и тесты source adapters с текущим кодом. Известный риск из предыдущего аудита — ошибочное представление сетевой ошибки как успешной пустой выдачи; текущую актуальность подтвердить запуском кода/тестов, не только текстом issue.
5. Проверить, как настроен Kilo именно в установленной версии. Существующие инструкции объединять, а не заменять. Сделать отдельный безопасный checkpoint/ветку только после проверки незакоммиченных изменений и явного выбора безопасного способа сохранения.

**Артефакты:** `docs/openmontage/FACTORY_AUDIT.md`, обновляемый `docs/openmontage/FACTORY_MASTER_PLAN_RU.md`, `docs/openmontage/OPENMONTAGE_RESUME.md`, `docs/openmontage/OPENMONTAGE_WORK_LOG.md` — создавать только после проверки существующих путей и не перезаписывать чужие файлы.

**Приёмка:** известны фактическая ветка и состояние Git; обнаруженные пользовательские изменения сохранены; бюджетный маршрут описан; понятно, какие стадии реально запускаются и какими тестами проверяются. Пока этот gate не пройден, никаких крупных рефакторингов, скачивания моделей, установки MCP или production-run.

### Сессия 2/6 — Kilo Code, минимальная команда агентов и skills

**Цель:** улучшить качество выполнения задач без раздувания архитектуры.

1. Настроить постоянные правила проекта: режим `$0`, запрет на разрушительные Git-команды, обязательное чтение project instructions, тест «сначала воспроизвести дефект», проверка diff, точная отчётность о тестах, provenance для фактов и активов, запрет публикации без человека.
2. Проверить доступные в текущей версии Kilo механизмы `AGENTS.md`, rules, custom modes, skills и subagents. Названия, форматы конфигурации и пути брать из документации соответствующей установленной версии, не копировать вслепую конфиг из примера другой версии.
3. Начать с главного агента-оркестратора и **трёх реально необходимых ролей**: `bug-hunter` (read-only), `research-evidence` (источники/доказательства без права менять код), `qa-reviewer` (read-only проверка результата). Роль тест-инженера подключить отдельно, когда есть проверяемая задача. Не создавать десятки почти одинаковых агентов.
4. Каждый субагент получает узкую задачу, ограниченный набор файлов/инструментов и фиксированный формат ответа: вывод, доказательства с путями/строками, риск, тест воспроизведения, предлагаемый минимальный следующий шаг. Главный агент отвечает за объединение результатов и проверку.
5. Отдельно проверять каждый skill/MCP/plugin: источник и лицензия, команды и права, внешние вызовы, передача данных, стоимость, необходимость, маленький тест и откат. Непроверенный или платный/неизвестной стоимости интеграционный маршрут не подключать.

**Артефакты:** проектные правила Kilo, матрица агентов/разрешений, allowlist инструментов, журнал решений по каждой интеграции. **Приёмка:** повторный запуск агента восстанавливает контекст из файлов; субагент не может публиковать/выполнять разрушительные команды; нет необязательных зависимостей, которые дублируют OpenMontage.

### Сессия 3/6 — доказательства, сценарий, storyboard и легальные медиа

**Цель:** подготовить для одного видео верифицируемый пакет до начала полноценного рендера.

1. Выбрать тему с понятной экономической «закулисной» историей: цепочка поставок, себестоимость, логистика, обслуживание инфраструктуры, скрытые бизнес-модели или экономика повседневного продукта. Сформулировать конкретный вопрос зрителя и оригинальную исследовательскую ценность.
2. Для каждого существенного фактического утверждения зафиксировать `claim_id`, точный текст, первоисточник/URL, цитируемый фрагмент или точные данные, дату доступа, тип источника, уровень поддержки, противоречия и статус факт-чека. Для наиболее значимых спорных/числовых утверждений искать независимое подтверждение. HTTP 200 не считается доказательством.
3. Сценарий должен ссылаться на реальные `claim_id`, а не придумывать ID. Оценка хука и «удержания» — редакционная подсказка, не прогноз просмотров и не замена проверки фактов.
4. Для каждой сцены определить `slot_id`, текст диктора, желаемый визуал, что именно кадр иллюстрирует, обязательные визуальные признаки, запрещённые несоответствия, примерную длительность и вид кадра: `literal`, `illustrative`, `archival` или `abstract`. Не выдавать иллюстративный кадр за доказательство конкретного события.
5. Искать сначала небольшое число релевантных кадров через существующие адаптеры OpenMontage. У каждого выбранного файла проверить права конкретного объекта, автора, условия использования/атрибуцию, URL, время получения и ограничения хранения. Для Pexels не строить постоянный массовый индекс/датасет без ясного разрешения; применить только разрешённый политикой источника способ работы.
6. Проверить выбранный временной отрезок несколькими кадрами, при важном действии — сам отрезок/последовательность. Similarity score CLIP и ответ VLM — сигналы для отбора, а не доказательство эпохи, места, личности или подлинности.

**Артефакты:** `research/evidence.json`, `script/script.md`, `storyboard/storyboard.json`, `assets/asset_manifest.json`, контактные листы кандидатов и отчёт по правам. **Приёмка:** ни одного выдуманного evidence/asset ID; все факты, требующие доказательства, имеют источник и статус; у каждого используемого клипа известны права/условия; спорные элементы честно помечены `REVIEW` или `BLOCKED`.

### Сессия 4/6 — вертикальный срез и завершённое пилотное видео

**Цель:** пройти весь реальный путь данных, сначала на 30–60 секундах, затем расширить его до целевого ролика 6–10 минут.

1. Прогнать 30–60-секундную сцену от research/evidence до реального лицензированного footage, narration, subtitles, timeline, render и QA. Не считать синтетические fixture/mocks реальным end-to-end результатом.
2. Проверить локальную английскую TTS на целевом оборудовании на 1–2 минутах реального сценария: качество голоса, произношение имён/чисел, задержка, потребление RAM/VRAM, условия лицензии модели/голоса и фактическая стоимость. Kokoro — кандидат для измеренного теста, не обязательная установка. Если ресурсы не подходят, не уходить автоматически в платный API: сравнить другой действительно локальный/разрешённый путь и задокументировать блокер.
3. Сопоставить длительность сцен с реальным аудио, синхронизировать subtitles по проверенным тайм-кодам. Не считать тайм-коды TTS точными до проверки. Музыка необязательна, если она отнимает время или мешает разборчивости речи.
4. Смонтировать полный пилот на 6–10 минут после успешного короткого среза. Использовать диаграммы/графики с данными и явной маркировкой как собственные визуализации; не подменять ими реальные свидетельства там, где зритель ожидает документальное footage.
5. Сохранять промежуточные артефакты, хеши входов, версии, stdout/stderr, состояние этапа и причины выбора медиа. Повторный запуск с теми же входами не должен заново выполнять уже завершённые дорогие/длительные операции.

**Артефакты:** тестовое видео, затем пилот `final_candidate.mp4`, субтитры, timeline/compose manifest, `run_manifest.json`, `qc-report.json`. **Приёмка:** реальный файл существует и воспроизводится; все стадии действительно исполнены; стоимость маршрутов проверена; пауза/перезапуск не приводит к потере утверждённых результатов.

### Сессия 5/6 — жёсткий QA, исправление ошибок и редакционная проверка

**Цель:** получить не просто MP4, а проверяемое видео, которое можно безопасно отдавать на ручную приёмку.

1. Запустить `ffprobe` и полный decode через `ffmpeg`; проверить длительность, разрешение, fps, кодек, потоки аудио/видео, чёрные/замороженные кадры, тишину, clipping/peak/loudness, subtitle timestamps, ошибки кодирования и целостность файла.
2. Сверить каждую сцену с `slot_id`, каждым asset — с source/license record, а каждый существенный claim — с evidence ledger. Проверить не только наличие файла/HTTP status, но и применимость прав/источника.
3. Выполнить визуальный просмотр целого ролика человеком: повторы, нерелевантные или вводящие в заблуждение кадры, произношение, плавность сцен, громкость, темп, соответствие заголовку/обложке, корректность цифр и утверждений. Машинная оценка не заменяет этот просмотр.
4. Добавить/починить regression tests на найденные дефекты: `no_results` отдельно от transport/auth/rate-limit failures; ноль пригодных клипов не является успехом; выдуманный ID блокируется; неизвестная лицензия/цена блокирует выход; broken media/тайм-аут/повтор job/resume обрабатываются корректно.
5. Устранить все блокирующие ошибки и повторно прогнать затронутые тесты и весь пилот. После существенного исправления не использовать прежний QC-отчёт как доказательство качества нового файла.

**Артефакты:** актуальный `qc-report.json`, список ручных замечаний, тестовые отчёты, финальный кандидат и решение `PASS / REVIEW / BLOCKED`. **Приёмка:** все hard checks пройдены; все права и evidence прослеживаются; открытые редакционные замечания явно перечислены. Публичная публикация по-прежнему запрещена без отдельного одобрения человека.

### Сессия 6/6 — фиксация процесса и ограниченное превращение в конвейер

**Цель:** превратить успешное разовое производство в воспроизводимую операцию, не включать массовый выпуск раньше времени.

1. Извлечь только повторяющиеся шаги, доказанные пилотом: закрепить manifest/schema, версионировать pipeline config, сделать этапы идемпотентными, сохранять входные fingerprints, результаты, ретраи и checkpoint после каждого этапа. Сохранять ошибку и состояние, а не превращать её в «пустой успех».
2. Разделить coding/repair runner и production runner. Не запускать два процесса записи над одними путями/state; использовать single-instance lock, lease/heartbeat и уникальный `job_id`. Не удалять lock без проверки владельца/heartbeat/процесса.
3. Добавить тесты resume, повторного job, параллельного запуска, остановки сети, rate limit, отсутствия клипов и неизвестного тарифа. В CI использовать fixture/mock-тесты; реальные сетевые/модельные интеграционные тесты запускать отдельно и явно.
4. Зафиксировать минимальную спецификацию ресурсов: свободное место, время рендера/TTS, пиковую RAM/VRAM, размер кэша, ограничение API, ручной труд и реальную стоимость. Не покупать сервер и не добавлять очередь/оркестратор, пока измерения не выявили узкое место.
5. Пройти минимум три последовательных полных E2E-прогона с отчётами и проверкой восстановления. Это ранний release gate, но не доказательство долгосрочной надёжности. После этого разрешается только ограниченный production pilot с ручной редакционной проверкой. Масштабировать число роликов/расписание — после наблюдения стабильности и ошибок.

**Артефакты:** pipeline manifest, схемы, тесты, recovery guide, work log, оценка времени/ресурсов, очередь тем и инструкция ручного выпуска. **Приёмка:** запуск детерминирован и восстанавливаем; бюджет остаётся $0; провал любого обязательного гейта блокирует публикацию; scheduler/upload выключены по умолчанию.

## 0.1. Kilo Code — целевая схема субагентов и разрешений

| Роль | Обязанности | Разрешения по умолчанию | Выходной контракт |
|---|---|---|---|
| `orchestrator` (главный Kilo) | План этапов, выбор следующей задачи, интеграция результатов, checkpoint | Чтение всего проекта; изменения только в одобренном scope; опасные/сетевые действия спрашивать | Решение и следующий шаг, изменённые файлы, тестовые факты, риски |
| `bug-hunter` | Поиск причины дефектов, репродукция, проверка edge cases | Read-only; без исправлений и публикации | Файл/строка, evidence, шаги воспроизведения, минимальный regression test |
| `research-evidence` | Источники, claims, разрешения на активы, противоречия | Доступ к web/источникам, но не к секретам и shell по умолчанию | Evidence records, URL/цитаты/дата, status `SUPPORTED/CONTRADICTED/UNCERTAIN` |
| `test-engineer` | Точечные/regression/contract tests | Изменять только тесты в выданном scope; без deploy/publish | Тест, команда, exit code, фактический результат |
| `qa-reviewer` | Независимая проверка diff, manifests, MP4 и отчёта | Read-only, отдельный от исполнителя | `PASS/REVIEW/BLOCKED`, замечания по severity и доказательства |
| `security-cost-auditor` | Секреты, права tool/plugin, лицензии, стоимость, fallback | Read-only, секреты не печатать | Матрица угроз/стоимости, провайдерные блокеры, разрешения |
| `visual-reviewer` (позже) | Сопоставление storyboard и реально выбранного фрагмента | Только media-кандидаты и shot briefs; не решает подлинность источника | Anchors observed, mismatch, uncertainty, рекомендация ручного просмотра |

**Правило запуска:** не все роли обязаны быть отдельными агентами в первом релизе. Если Kilo/модель не поддерживает изолированные права, не объявляй их изолированными: исполняй роли последовательными задачами с ручной проверкой. Избегай нескольких агентов, одновременно пишущих в одни файлы. Субагент предлагает; оркестратор проверяет; пользователь одобряет существенные изменения и публикацию.

### Настройка Kilo: порядок и ограничения

- На старте прочитать `AGENTS.md`; если корневого файла нет — предложить минимальный новый. При наличии `AGENT_GUIDE.md`/`PROJECT_CONTEXT.md` не затирать их и зафиксировать, какой файл является главным источником инструкций.
- Использовать built-in Plan/Read-only для аудита, Debug для воспроизведения, Code для одной узкой одобренной задачи. Проверить актуальные названия режимов и конфигураций в текущей версии Kilo до редактирования файлов.
- Разместить короткие правила по темам (Git safety, $0 routing, provenance/licensing, testing/QA, resume) в поддерживаемом проектном механизме. Не копировать один и тот же огромный промпт во множество файлов: общие правила — в основном файле; детали — в отдельной skill/документации этапа.
- Для каждой задачи указывать: цель, точный scope, что запрещено, воспроизведение дефекта, критерии приёмки, нужные тесты, ожидаемые файлы и формат отчёта.
- Включить подтверждение перед удалением/перезаписью файлов, stop/kill процессов, удалением lock/checkpoint, сбросом Git, действиями с секретами, внешней загрузкой, публикацией и потенциально платным вызовом. Не включать unrestricted auto-approve.
- Каждый результат записывать в checkpoint: `current_stage`, `job_id`, input/output fingerprints, завершённые этапы, незавершённые задачи, последний проверенный commit/HEAD, тесты (команда/exit code), артефакты, провайдеры/стоимость, блокеры и следующий безопасный шаг. Не сохранять секреты и приватные токены.

## 0.2. Skill-пакет: что взять из YouTube Agent Skill, а что не путать с фабрикой

Репозиторий: [Jakeschincariol/youtube-agent-skill](https://github.com/Jakeschincariol/youtube-agent-skill). По доступному исследованию в нём описаны 11 навыков и несколько лёгких Python-утилит. Это вспомогательный слой для разработки и упаковки контента, а не замена OpenMontage: он сам по себе не обеспечивает лицензированный поиск footage, TTS, timeline, рендер и полный технический QA.

| Skill | Решение для OpenMontage | Адаптация/ограничение |
|---|---|---|
| `yt-script` | Взять идею и адаптировать в первую очередь | Хуки и ритм удержания; сценарий обязан включать `claim_id`/evidence, никаких выдуманных фактов |
| `yt-package` | Взять после сценария | Проверки заголовка и обложки; не обещает CTR и не разрешает вводящий в заблуждение кликбейт |
| `yt-chapters` | Можно взять рано | Проверка глав по реальным timestamps финального видео/субтитров |
| `yt-seo` | Взять после ручного утверждения видео | Metadata как пакет предложений, не автоматическая публикация |
| `yt-shorts` | Отложить до стабильного long-form | Разметка пригодных сегментов; требует проверки контекста и смысла вырезанного фрагмента |
| `yt-edit` | Опционально | Edit decision list по субтитрам помогает монтажу, но сама по себе не редактирует настоящий видеоряд |
| `yt-retention` | После первых опубликованных видео и появления своих CSV | Анализ реальных retention данных; не выводить поведение аудитории из выдуманных/примерных данных |
| `yt-viral` | Позже, если есть достаточная история канала | Outlier относительно медианы — ретроспективная метрика, а не предсказатель вирусности |
| `yt-audit` | Позже | Анализ канала/видео после наличия фактических данных |
| `yt-comment` | Не входит в первую версию фабрики | Доступ к комментариям/подготовка ответов требует проверки источника данных и отдельного человеческого контроля |
| `yt-plan` | Лёгкий необязательный модуль | Планирование очереди тем; использовать только с данными исследований и ограничениями производственной мощности |

**Правило приёмки каждого skill:** прочитать весь `SKILL.md` и все вызываемые скрипты/конфиги; проверить лицензию, доступ к сети, чтение/запись, секреты, внешние зависимости и команды; прогнать на fixture; сравнить качество с простой ручной задачей; зафиксировать источник/commit/hash; иметь возможность отключить без ломки pipeline. При подтверждении лицензии и совместимости копировать цельный каталог вместе со скриптами и нужными данными, не один описательный файл. Результат оценки хука — эвристика, не достоверный прогноз будущих просмотров.

## 0.3. Plugins и MCP: минимум интеграций, максимум контроля

Не добавлять plugin/MCP «на всякий случай». Сначала проверить встроенные средства Kilo и имеющийся OpenMontage toolchain. Интеграция допускается только если она закрывает конкретную отсутствующую функцию, имеет ясную лицензию/условия, доказуемо совместима, укладывается в $0 и прошла минимальный тест.

1. **Допустимые кандидаты на рассмотрение:** документация/поиск источников; доступ к GitHub преимущественно read-only для анализа; локальные media/QA tools; MCP для конкретного провайдера данных только если официальные условия и права на скачивание/кэш понятны. Кандидат не означает, что он уже установлен или одобрен.
2. **Не включать в первом пилоте без необходимости:** YouTube upload API; управление каналом/комментариями; произвольный browser automation; универсальный MCP с широким shell/filesystem доступом; платные LLM/TTS/image/video API; маршруты с неизвестным биллингом.
3. **Перед установкой записать:** имя/URL репозитория, версию/commit, лицензию, capabilities, permissions, домены/сеть, файлы и секреты, стоимость, квоты, тест, rollback и владельца решения.
4. **Fail-closed:** неизвестная цена, необходимость секретного ключа с неясными условиями, скрытый платный fallback, неразборчивая телеметрия, чрезмерные права или отсутствие способа отключения → отклонить до проверки.

## 0.4. Обязательные схемы данных и состояния

Минимум следующие интерфейсы должны быть стабильными и проходить schema validation до того, как этап использует их данные. Поля ниже — минимальный контракт проекта, а не утверждение, что такие схемы уже существуют в репозитории.

**`evidence_record`:** `claim_id`, `claim_text`, `source_url`, `source_title`, `publisher_or_author`, `published_at` (если известно), `accessed_at`, `supporting_excerpt_or_data`, `source_type`, `independent_confirmation_ids`, `contradictions`, `fact_check_status`, `review_note`. Неподтверждённое значение не заполнять догадкой; использовать `null`/`UNKNOWN` согласно схеме.

**`asset_record`:** `asset_id`, `slot_id`, `provider`, `source_url`, `creator`, `license_name`, `license_url_or_terms`, `attribution_text`, `retrieved_at`, `local_path`, `sha256`, `source_clip_id`, `in_sec`, `out_sec`, `duration_sec`, `width`, `height`, `fps`, `rights_status`, `storage_policy`, `visual_match_status`, `match_reason`, `reviewer`, `notes`. Отсутствие лицензии или понятного основания использования означает `BLOCKED`.

**`stage_checkpoint`:** `job_id`, `stage_id`, `stage_version`, `status`, `input_fingerprint`, `output_paths`, `output_hashes`, `attempt`, `started_at`, `finished_at`, `tool_versions`, `provider_route`, `cost_usd` (неизвестное — `null`, но при этом запуск блокируется), `warnings`, `errors`, `validation_report`, `resume_from`. Не писать секреты в manifest/log.

Состояния не смешивать: `PASS` = выполнен и проверен; `REVIEW` = нужен человек; `BLOCKED` = отсутствует обязательное условие/разрешение; `FAILED` = стадия исполнялась и завершилась ошибкой; `NOT_RUN` = не запускалось. Пустая выдача поиска — отдельный `NO_RESULTS`, а не transport-success и не ошибка, скрытая за пустым массивом.

## 0.5. Go / No-Go — обязательные блокирующие правила

**NO-GO для рендера как publishable-кандидата**, если отсутствует существенное подтверждение факта, есть невалидный ID, права на используемый медиафайл не установлены, требуемая сцена не имеет подходящего актива, стоимость провайдера неизвестна/положительна в режиме `$0`, stage manifest невалиден, медиа повреждено, обязательная QA-проверка не прошла или рендер не соответствует утверждённым входам.

**NO-GO для автоматического конвейера**, если нет idempotency/checkpoint/resume, защита от второго writer не тестировалась, реальные сетевые ошибки маскируются как `NO_RESULTS`, отсутствует повторяемый E2E сценарий, не измерено потребление ресурсов или нет уведомления о сбое. Три успешных E2E — ранний gate для ограниченного пилота, не доказательство долговременной надёжности.

**NO-GO для публикации** всегда без отдельного явного человеческого одобрения финального файла, заголовка, обложки, описания и прав на использованные материалы. Фабрика может подготовить пакет; она не должна сама решать, что он публично опубликован.

## 0.6. Оптимизации: что не делать до доказанного узкого места

- Не переписывать OpenMontage и не вводить LangChain/Prefect/Temporal/LanceDB/FiftyOne только ради «более агентной» архитектуры; сначала использовать существующие stage skills, tools, schemas, manifests и checkpoint-механизмы.
- Не строить глобальный индекс активов всех источников сразу. Сначала доказать качество прямого поиска на пилоте; правила индексации разные у каждого поставщика.
- Не разворачивать Qwen/VLM или другие большие модели до замера оборудования и малого benchmark. Сначала контакт-лист и проверка человеком, дальше измеренный VLM как подсказка.
- Не делать дорогие real-provider calls в обычном CI. Unit/contract tests должны работать на фиксированных fixtures без API key/сети; реальные smoke tests запускаются отдельно.
- Не смешивать coding runner и video production runner, не разрешать двум процессам изменять общие manifests/папки. Не кэшировать неподтверждённые выходы как успешные.
- Не ставить расписание и не производить десятки видео до одного вручную принятого пилота и регрессионного набора.

## 0.7. Приоритетный backlog

**P0 — сначала:** (1) read-only audit рабочего дерева и Kilo configuration; (2) подтверждение строгого `$0` guard до любого внешнего вызова; (3) проверка и тестирование всех source adapters, включая риск issue #511; (4) единые схемы evidence/asset/stage status и запрет выдуманных ID; (5) безопасные checkpoint/resume и отчёт о каждой задаче.

**P1 — один видео-пилот:** (1) исследование → сценарий с evidence → storyboard; (2) небольшой набор footage с подтверждёнными правами; (3) тест локальной озвучки на реальном железе; (4) короткий вертикальный срез; (5) ролик 6–10 минут; (6) `ffprobe` + full decode + visual/editorial QA и ручное решение.

**P2 — повторяемость:** (1) regression tests для сети/пустых выдач/платного fallback/повреждённых активов; (2) resume/idempotency и lock contract; (3) pipeline schema/config; (4) сбор метрик времени/ресурсов/ручных правок; (5) ограниченный production pilot после трёх успешных полных прогонов.

**P3 — только после данных:** улучшение поиска/моделей, ограниченный visual benchmark и auto-accept на подтверждённой precision, дополнительные skills и упаковка, автоматизация публикации (всё ещё с подтверждением человека), масштабирование и планировщик.

## 1. Что было ошибочно или недостаточно определено

### A. Индексация Pexels — высокий лицензионный риск

В прежнем плане предлагалось развивать повторно используемый корпус через `corpus_builder` + `clip_search`. Это нельзя автоматически применять ко всем источникам. В актуальных условиях Pexels запрещает неразрешённое массовое/систематическое копирование и сбор изображений, видео или метаданных для создания датасетов и разработки ML/AI-моделей. Постоянный большой индекс Pexels-клипов/эмбеддингов может попасть в эту запрещённую область. Пока у нас нет явного разрешения и юридически понятного режима, **не строить глобальный reusable corpus из Pexels**. Использовать API точечно для конкретного видео; сохранять только нужные лицензированные активы и атрибуцию для проекта. Кэшировать API-ответы только в допустимых пределах; Pexels рекомендует кэш как способ беречь квоту, но это не разрешение на bulk download или датасет. Лимиты по умолчанию: 200 запросов/час и 20 000/месяц; не рассчитывать на снятие лимита — условия меняются.

В коде необходимы разные политики на источник: `query_only`, `per_project_asset`, `temporary_cache`, `persistent_index_allowed`, `needs_permission`. Для Pexels выставить запрет постоянного индекса до разрешения. Для Archive.org, Wikimedia, NARA, NASA, NOAA, ESA/JAXA и других архивов также проверять права на конкретный объект и правила доступа/массовой загрузки — название архива не гарантирует, что каждый файл public domain.

Официальные страницы: [Pexels API docs](https://www.pexels.com/api/documentation/), [Pexels Terms summary (updated Oct 10, 2026)](https://help.pexels.com/hc/en-us/articles/900005880463-What-are-the-Terms-and-Conditions), [Pexels rate-limit information](https://help.pexels.com/hc/en-us/articles/900005852323-How-do-I-get-unlimited-requests).

### B. Проверка URL в AI Video Factory — не полноценный факт-чек

[AI Video Factory `source_verifier.py`](https://github.com/summitsingh/ai-video-factory/blob/main/src/ai_video_factory/source_verifier.py) проверяет формат URL, placeholder-адреса и HTTP-статус. Это полезная проверка ссылок, но HTTP 200 не говорит, подтверждает ли статья утверждение, достаточно ли авторитетен источник и не противоречит ли ему другое исследование. Перенимаем архитектуру provenance/отчёта, но отдельно реализуем `claim → source → excerpt/evidence → support status`, независимое подтверждение ключевых фактов и журнал разногласий.

### C. Проблема source adapter остаётся реальной

[OpenMontage issue #511](https://github.com/calesthio/OpenMontage/issues/511) по состоянию на проверку открыт. Он описывает ложный успех, когда сетевой сбой превращается в пустой список, а `direct_clip_search` может показать `success=True`, `clips_downloaded=0`, `errors=[]`. В текущем `tests/tools/test_stock_source_adapters.py` строгими ожидаемыми сбоями помечены `archive_org`, `wikimedia` и `pond5_pd`. Текст issue также упоминает несколько адаптеров, которые могли глотать ошибки на момент сообщения; нельзя считать каждый из них подтверждённо сломанным сейчас. Правильное действие: запускать текущий тест на **всех зарегистрированных адаптерах**, чинить все падения и сохранять контракт: пустая выдача ≠ transport/auth/rate-limit failure.

### D. CLIP + VLM — оценка соответствия, а не доказательство

CLIP — быстрый retrieval/ranking, но тематически похожий кадр может быть неверным по действию, времени, месту или эпохе. VLM тоже может ошибаться, а его словесная `confidence` не является откалиброванной вероятностью. Проверять несколько кадров из выбранного отрезка, а не единственную миниатюру; для важных действий проверять последовательность кадров/сам фрагмент, а не только статичную картинку. Историческая подлинность всегда проверяется по provenance и источникам отдельно от визуального содержания.

Не копировать порог `0.22` из upstream как универсальную истину. Значения similarity зависят от модели, данных и запроса. Создать тестовый набор с человеческой разметкой и пороги выбирать по измеренной точности; если точность не подтверждена — статус `REVIEW`, не auto-accept.

### E. TTS timestamps требуют проверки

[Kokoro-FastAPI](https://github.com/remsky/Kokoro-FastAPI) заявляет локальный OpenAI-совместимый endpoint и тайм-коды на уровне слова или чанка; [Kokoro-82M](https://huggingface.co/hexgrad/Kokoro-82M) имеет метку Apache-2.0. Это хороший кандидат, не гарантия качества на нашем оборудовании. Зафиксировать конкретный release/tag, проверить произношение, тайминги и скорость на нашей машине. `faster-whisper` использовать как опциональную проверку реально произнесённого текста/тайм-кодов, не как факт-чек; ASR тоже может ошибаться.

### F. Три прохода — полезный минимум, но не гарантия стабильности

Три последовательных полного E2E — разумный ранний smoke gate. Для включения расписания этого недостаточно само по себе: требуются regression tests, проверка восстановления после сбоя, лицензий, бюджета и визуального gold set, а затем ограниченный пилот с ручной проверкой результата и оповещением при падениях.

### G. Лицензия OpenMontage

OpenMontage распространяется под AGPL-3.0. Для личной работы это не запрещает использовать проект, но перед распространением модифицированной версии или предоставлением сетевого доступа пользователям необходимо проверить обязательства AGPL, включая требования к исходному коду соответствующей модификации. Не копировать файлы/фрагменты кода из других репозиториев без фиксации лицензии и сохранения требуемых уведомлений.

| [Qwen3-VL-2B-Instruct](https://huggingface.co/Qwen/Qwen3-VL-2B-Instruct) | Опциональный локальный visual reviewer | Веса `model.safetensors` около 4.26 GB плюс дополнительная RAM/VRAM; не устанавливать до аудита оборудования. Apache-2.0. Проверить на gold set; не считать ответы истиной. |
| [PySceneDetect](https://github.com/Breakthrough/PySceneDetect) | Опционально | Подключать только если имеющееся извлечение кадров/сцен недостаточно. |
| [Shorts Factory](https://github.com/nightskat/shorts-factory) | Идеи резюмируемых заданий | Не брать за основу длинного documentary pipeline; некоторые интеграции у проекта оставались незавершёнными. |
| [Faceless Video Pipeline](https://github.com/JEMA-Software-Ltd/faceless-video-pipeline) | Идеи измерения длительности и простого QC | Не копировать целиком; проектный охват уже нашей задачи. |
| LanceDB / FiftyOne / Prefect / Temporal | Отложить | Не добавлять без измеримого bottleneck. Использовать простые checkpoints и существующий runner до тех пор, пока это работает. |

## 3. Целевая архитектура

`topic queue → research → evidence ledger → script → fact-check → storyboard/shot brief → legal-aware footage search → visual alignment QA → TTS → transcript/alignment QA → timeline/audio mix → FFmpeg render → technical QA + editorial QA → package → manual approval`.

Каждый этап принимает/возвращает schema-validated JSON/файлы и записывает: `stage_status`, version, input fingerprint, attempts, provider/cost decision, output paths, warnings, validation report. Состояния различать строго: `PASS`, `REVIEW`, `BLOCKED`, `FAILED`. Повтор шага должен быть idempotent и не оплачивать/скачивать/генерировать заново успешные артефакты. Не запускать coding runner и production runner одновременно над теми же путями/state.

## 4. План внедрения по приоритетам

### P0 — контроль бюджета, права, ошибки

1. Сначала получить свежий read-only аудит Kilo: git status/branch/HEAD/diff, архитектура и реальные этапы, процессы/locks/checkpoints, тесты и конфиги. Ничего не останавливать, не удалять и не менять до аудита.
2. Установить guard на **самой границе каждого провайдерского вызова**: allowlist конкретного маршрута, провайдера и текущего условия free tier; неизвестная стоимость/неизвестное entitlement → `BLOCKED`; никакого платного fallback; не делать сетевой запрос до принятия решения о маршруте. `budget_default_usd=0` сам по себе недостаточен. $0 означает отсутствие прямых платных API/лицензионных расходов; электричество, вычисления, диск и интернет всё равно имеют стоимость.
3. Исправить ложные успехи media adapters. Для каждого зарегистрированного адаптера проверить timeout, DNS/connection failure, 429, 403, 5xx, пустой настоящий ответ, malformed response и partial cascade. При всех ошибках источник помечается `ERROR`; при реальной пустой выдаче — `EMPTY`; при частичном успехе сохраняются warnings. Если слот не получил ни одного валидного кандидата — эпизод `BLOCKED`, если fallback не заполнил слот.
4. Убрать выдуманные source/evidence/clip IDs; ссылки должны разрешаться в существующие записи. Плейсхолдеры/пустые URLs блокируют этап.
5. Ввести policy manifest по каждому источнику и per-asset provenance: `provider`, `source_url`, asset page, author/creator, license identifier + URL, credit text, restrictions, retrieved timestamp, checksum, allowed storage modes, chosen clip in/out. Unknown terms => не использовать автоматически. Генерировать `credits.txt` и блок атрибуции для описания ролика.
6. Для Pexels запретить bulk/global embeddings corpus без разрешения; сначала использовать on-demand candidate searches и только проектные активы. Квоты учитывать, повторные запросы кешировать в разрешённых условиях. Добавить этот policy в код/тесты, не только в инструкцию.
7. Разделить живой issue #511 с known strict xfails и все остальные адаптеры тестировать; не считать статус issue доказательством конкретного текущего дефекта без актуального test.

### P1 — один end-to-end документальный ролик

8. До новых зависимостей собрать 30–60-секундный тест: проверяемая тема, доказательства, сценарий, 3–6 реальных клипов, голос, музыка/микс, субтитры, MP4, thumbnail/metadata draft. Если нынешние источники не обеспечивают всё, это оформить как конкретный блокер.
9. Для быстрого вертикального среза использовать `direct_clip_search` + contact sheet. Когда работает, улучшить retrieval, но применять `corpus_builder` только к источникам/активам, для которых разрешена такая форма постоянной индексации. Не строить один общий индекс всех провайдеров без различения политик хранения.
10. Зафиксировать `asset_manifest` как интерфейс между search, visual QA и renderer. Поля минимум: `slot_id`, scene type, required visual anchors, forbidden mismatches, clip ID/path, segment in/out, search score, provider, rights record, QA outcome, QA model/version, reviewer reason, final timeline range.

### P1 — Visual Alignment QA (проверка попадания футажа в текст)

11. Для каждого фрагмента озвучки storyboard формирует короткий `shot brief`: что должно быть видно, действие, объект, эпоха/локация если важны, тип `literal / illustrative / archival / abstract`, а также запрещённые несоответствия. Различать «иллюстрирует тему» и «документирует конкретное событие».
12. Stage A: CLIP ранжирует несколько кандидатов (не только один). Stage B: для выбранного временного участка взять несколько кадров распределённо плюс кадры около границ; для действия проверить последовательность/движение, а не один кадр. Stage C: опциональный Qwen3-VL выдаёт строго структурированный `match / mismatch / uncertain`, наблюдаемые anchors и причины. Модель не должна выдумывать даты/географию, которых не видно.
13. Настроить benchmark из 50–100 вручную размеченных сцен: настоящие совпадения, тематически похожие ошибки, неверная эпоха/локация, неподходящее действие, плохое качество, дубли. Разделить train/dev и holdout; не настраивать порог на том же наборе, на котором оцениваем результат. В CI использовать сохранённые кадры и mock/фиксированную модель; реальный VLM benchmark запускать отдельно.
14. Автоматически принимать только те случаи, где проверенный на holdout порог достигает целевой precision; иначе `REVIEW`. Не использовать LLM self-confidence как единственное решение. Если требуется установить факт «это событие 1977 года», визуальная модель не подтверждает историческую подлинность: нужны provenance и надёжные письменные источники.

### P1 — английская озвучка, субтитры и микс

15. Протестировать Kokoro-FastAPI локально на реальном 60–120-секундном английском сценарии: 2–3 голоса, собственные имена/даты/числа, длинные фразы, скорость генерации, артефакты, разрывы между chunk. Зафиксировать tag/digest; не использовать `latest` для стабильного production без pinning. Не включать voice cloning в первый релиз.
16. Сопоставить timestamps TTS с реальным аудио. Если проверка транскрипта нужна, faster-whisper транскрибирует итоговую дорожку; сравнить нормализованный текст с утверждённым скриптом, а имена и числа выделять отдельными checks. ASR не доказывает факты и может ошибаться.
17. Сохранить текущий FFmpeg renderer. Выполнить измеряемые проверки loudness/peak, clipping, silence, stream metadata, длительности, полного decode и синхронизации субтитров. Добавить `ffmpeg-normalize` только если встроенный `loudnorm`/текущий audio mixer недостаточен.

### P1/P2 — регрессия и расписание

18. Автоматические тесты: фиктивный ID; source URL placeholder; 200 URL с нерелевантным контентом; противоречивые claims; неизвестная лицензия; запрещённая storage policy Pexels; реальная пустая выдача vs timeout/429/403/5xx; повреждённый клип; неверное разрешение/aspect; отсутствующий звук; неверные subtitles/timestamps; model route unknown/paid; повторный запуск checkpoint; повторная работа двух runner.
19. В CI — unit/contract/regression tests, `ruff`, dependency/security checks (например `pip-audit`, secret scan) если совместимы с текущей средой. Не включать платные сетевые вызовы или скачивание моделей в обычный CI. GPU/сеть — отдельный opt-in test group.
20. Release gate: все блокирующие тесты зелёные; ни один paid/unknown-cost route не вызван; лицензии/права известны для всех клипов; каждая фактическая фраза привязана к evidence; все сцены имеют валидный asset или обоснованный `REVIEW/BLOCKED`; MP4 проходит полный decode и все hard checks; визуальная QA прошла benchmark. Сделать минимум 3 E2E прогонов подряд как smoke gate, затем вручную проверить серию роликов в целевой длительности и восстановление после отключения сети/падения процесса.
21. Только после этого включить **ограниченный schedule pilot** на persistent host с durable storage, checkpoint recovery, алертингом и очередью 7–14 тем. Не считать Codespaces постоянно включенным сервером. Первые публикации вручную; YouTube upload API сначала только private/unlisted. Публичный upload/API доступ также зависит от состояния проекта/аудита Google API.

## 5. Как проверить качество, а не только наличие MP4

**Hard failures:** отсутствует evidence/asset/licence; paid/unknown route; невалидный schema/ID; нулевые клипы; FFmpeg decode error; нет аудиопотока; неверная длительность/разрешение; subtitles уходят за аудио; повреждённый/пустой output.

**Editorial review:** факт не имеет достаточного подтверждения; спорный источник; визуальный клип похож по теме, но не соответствует действию/эпохе; историческая authenticity неизвестна; голос неправильно произносит имя; слишком повторяющиеся кадры; музыка заглушает речь; ролик выглядит шаблонным без самостоятельной ценности.

**Сигналы метрик:** доля клипов, принятых с первого раза; precision на визуальном holdout; доля заблокированных слотов; частота source transport failures; доля ручного исправления субтитров; rerender rate; время/диск на ролик; фактические расходы на провайдеров (должны быть $0 при zero-dollar режиме). Отслеживать результаты по темам, а не скрывать ошибки в среднем показателе.

## 6. Kilo Code: рабочий протокол

1. Сначала read-only audit и конкретный список файлов/команд/рисков. Не менять конфиги, не запускать модели и не трогать процессы до одобрения.
2. Дальше одна небольшая задача за раз: цель → scope → ограничения → критерии готовности → тесты → отчёт.
3. Перед фиксами — test reproducing bug; после фикса — regression test, тестовый набор и diff. Если команда не запускалась, не говорить «прошло».
4. Разделить coding agent и read-only reviewer/bug-hunter. Избегать параллельной записи в одни файлы.
5. Не показывать/логировать секреты, не делать платные API calls, не удалять locks/checkpoints/outputs и не публиковать без явного разрешения.
6. Поддерживать `AGENTS.md` с текущей архитектурой, командами тестирования, бюджетом, лицензиями и запретами; обновлять его после подтверждённых изменений, не предположений.

## Следующее действие

Когда приходит отчёт Kilo — сверить его с пунктами P0 и выбрать **один фактический блокер**, затем попросить Kilo реализовать минимальный фикс вместе с regression test. Пока не устанавливать Kokoro/Qwen, не расширять индекс, не менять основной pipeline и не запускать расписание до проверки среды и кода.
